# CLAUDE.md

Контекст проекта для Claude Code. Прочитай этот файл перед началом работы.

## Что это за проект

Solo Leveling Daily Training (SLDT) — локальный фитнес-трекер ежедневных заданий в визуальной стилистике манхвы/аниме Solo Leveling. Это **трекер с игровыми элементами**, а не игра с элементами трекера — важное разграничение, зафиксированное с пользователем явно: никаких виртуальных событий (подземелья, врата, битвы с монстрами и т.п.), только реальные упражнения (отжимания, приседания, подтягивания, пресс, шаги) с игровой надстройкой (уровни, ранги, титулы, артефакты, магазин).

Репозиторий на GitHub: `solo-leveling-tracker`.
Текущая версия: **v5.9.62**.

**ПРАВИЛО (с v5.9.54): все цены новых предметов должны быть чётными числами** — чтобы продажа за 50% всегда давала целое число без необходимости полагаться на `Math.floor()` как единственную защиту.

**ПРАВИЛО (с v5.9.43): при каждой сборке, где меняется `APP_VERSION`, строка «Текущая версия» в README.md обновляется в обязательном порядке — тот же чек-лист, что уже применяется к обновлению этого файла (`CLAUDE.md`).**

## Технологии и структура файлов

Никакого билд-процесса, фреймворков или npm-зависимостей. Чистый HTML/CSS/JS.

```
index.html      — всё приложение: разметка, стили (<style>), логика (<script>) в одном файле
manifest.json   — PWA-манифест
sw.js           — Service Worker (кэширует приложение + иконки + шрифт Orbitron для офлайна)
icons/          — иконки приложения (сгенерированы из исходного логотипа, разные размеры/назначения)
```

Все данные пользователя хранятся в `localStorage` (два ключа: состояние прогресса и суммарная статистика за всё время). Никакого бэкенда, никакой синхронизации между устройствами — экспорт/импорт прогресса через файл `.json` или код в буфере обмена (обе опции живут в модалке «АРХИВ»).

## Версионирование и совместимость сохранений

- Номер версии указан в `<title>` и в `#limitBreakContainer`/шапке — держи его синхронизированным при правках.
- Ключи `localStorage` версионируются (`sl_daily_vX_Y_Z`, `sl_total_stats_vX_Y_Z`). Список `PREV_KEYS`/`PREV_STATS_KEYS` в начале скрипта — цепочка миграции старых сохранений на новый ключ.
- **Бампать ключ хранения нужно только при изменении структуры данных**, а не при чисто косметических/визуальных правках — иначе накапливается мусор миграций. Чисто CSS/текстовые правки (примеры — v5.5.1–v5.5.7) номер ключа не меняли.
- При добавлении нового поля в объект `data`: обязательно добавить его (а) в дефолт для чистой установки, (б) в блок миграции старых сохранений с фолбэком, (в) в защитную нормализацию сразу после загрузки (на случай кривых/старых данных), (г) в `sanitizeImportedData()` для валидации при импорте бэкапа.
- `sw.js` имеет свою переменную `CACHE_VERSION` — её нужно бампать при каждом изменении любого закэшируемого файла (`index.html`, иконки, манифест), иначе часть пользователей будет видеть версию из кэша.

## Ключевые игровые системы (кратко, для ориентира)

- **Квесты**: 5 заданий в день (pushups/squats/pullups/press/steps), цель на день считается через `getDynamicTarget()` — растёт с уровнем, но с уровня 1 по 10 действует щадящий множитель (0.5×→1.0× линейно, `getBeginnerMultiplier()`), дальше — обычный рост. Награда (`getDynamicExp()`) от этого множителя **не зависит** — награда всегда полная, это осознанное решение.
- **Уровни/ранги**: EXP → левел-ап → ранг (E/D/C/B/A/S/National/SSS/Shadow Monarch) через `getRank()`.
- **Титулы**: иерархия значимости `TITLE_PRIORITY` (важнее → менее важно). Новый титул авто-надевается только если он значимее текущего активного; иначе просто добавляется в список. Ручной выбор — клик по карточке в Инвентаре. «Целеустремлённый» требует непрерывной серии 7 дней и полностью пропадает при её прерывании.
- **Преодоление предела**: разблокируется с 3 уровня (кнопка физически скрыта до этого момента), 2 использования в день (плюс бонусы от артефакта/статов/расходников — см. версии v5.8.0+), сбрасывается ежедневно. Расположена выше сетки 2×3 (между последним упражнением и кнопками), визуально отделена разделительной линией.
- **Система штрафов**: пропуск дня снимает % EXP (зависит от уровня/силы/артефактов), показывает модальный баннер с суммой. Руна Защиты — расходник, отменяет штраф на следующий день.
- **Характеристики**: пять статов — Сила (STR), Ловкость (AGI), Выносливость (STA), Интеллект (INT), Восприятие (PER), в этом порядке на экране. Очки начисляются при левел-апе (база + бонусы от артефактов роста статов), распределяются вручную. Подробности эффектов каждого стата и цифры — см. записи v5.9.9–v5.9.10.
- **Системные уведомления**: 3 типа (утро/срочно/выполнено), у каждого 2–3 обезличенных варианта текста (Система обращается как «Игрок», никогда не по имени — так по лору первоисточника). Показываются не чаще раза в день, флаги в `data.dailyNotices`.
- **Имя игрока**: спрашивается один раз при первой установке (не при миграции старых сохранений), хранится в `data.playerName`, можно сменить из «АРХИВА». Фолбэк-подпись — «Игрок» (не «Охотник» — сознательно отвергнутый вариант).
- **Журнал/календарь («Летопись»)**: отдельная кнопка (не вкладка — так было в v5.6.0, переделано в v5.7.0). `data.history` — запись на каждый день (статус success/penalty/protected + опционально достигнутый уровень), ключ — календарная дата **начала** цикла заданий (сдвиг через полночь до 5 утра учтён в `checkMissedDays()`, дата берётся от `data.lastReset` до его обновления). `data.bestStreak` — рекорд серии, обновляется в `applyPenaltyLogic()`. `data.pendingLevelUpToday` — служебное поле, перезаписывается на каждый левел-ап в течение дня, «прикрепляется» к записи истории при суточном сбросе и обнуляется. История ведётся с нуля от даты обновления (ретроактивно не восстанавливается — это ожидаемо). Цвета: зелёный/красный/синий — обводка+свечение (не заливка), сегодняшний день — рамка из 4 уголков синим. Пурпурный в календаре не используется — он закреплён только за рангом Shadow Monarch.
- **Кодекс Системы**: отдельная кнопка, список глав (`CODEX_CHAPTERS`) с **индивидуальной нумерацией** — `data.codexUnlocked` хранит порядок открытия лично у этого игрока (не привязан к теме), поэтому дыр в номерах не бывает. Базовые главы (`daily_quota`, `penalty`, `chronicle`, `shop`, `boxes`, `archive`, `stats`) есть у всех с самого начала без уведомления. Остальные главы (ранги через `RANK_CODEX_MAP`, артефакты `artifact_*`, три титула через `TITLE_CODEX_MAP`, `limit_break` — с 3 уровня) открываются функцией `unlockCodexChapter(id)`, которая уведомляет («Записано в Кодекс: …») и является идемпотентной (безопасно вызывать повторно). Чтобы добавить новую главу под будущий предмет/фичу — просто дописать запись в `CODEX_CHAPTERS` и вызвать `unlockCodexChapter()` в нужном месте, механизм это и есть весь его смысл.
- **Прогресс**: отдельная кнопка, показывает то, что раньше было текстом на главном экране («Общий прогресс за всё время»).
- **Нижние кнопки**: сетка 2×3 (`sub-menu-grid`) — Кодекс/Летопись/Архив, Магазин/Инвентарь/Прогресс.
- **Очередь системных уведомлений**: единый механизм (`enqueueNotification`/`processNotificationQueue`/`displayNotificationNow`) для ВСЕХ типов сообщений (короткие баннеры через `showNotice()`, объявления о ранге/титуле через `showSystemPopup()`, Кодекс). Не более одного на экране одновременно, автозакрытие через 10 секунд или тап раньше, пауза 2 секунды между показами. Не путать с `.levelup-popup`/`.complete-popup` — те не участвуют в очереди, это отдельные визуальные эффекты.
- **Журнал уведомлений за сутки**: `data.notificationLog` (время + текст, самые новые сверху), пишется в `logNotification()` при каждом показе, сбрасывается при суточном сбросе. Доступ — кнопка «Уведомления системы» в «АРХИВЕ» (секция «Игрок»).
- **Напоминания о невыполненном задании**: категория переименована из «Срочно» в «reminder» (в коде: `SYSTEM_NOTICES.reminder`/`reminderUrgent`). Проверяется каждый час в окне 10 часов до сброса (`checkReminderNotice()`, `data.remindersFiredHours` — какие часовые отметки уже показаны сегодня), последние 2 часа — более настойчивый пул текстов. Прекращается сразу при выполнении задания.
- **Защита от повтора текста**: `pickRandomNoRepeat(pool, category)` — не показывает тот же текст, что был в прошлый раз в той же категории (`data.lastNoticeText`). Используется для morning/complete/reminder.

**v5.7.11 — ревизия баланса прокачки (важно для будущих правок).**

Проблема, которая привела к этой правке: старая формула опыта (`1000 × 1.15^уровень`, экспоненциальная) в паре с бесконечно растущими дневными целями (`+5%/уровень`, тоже без потолка) означала, что после ~30 уровня прогрессия математически упиралась в стену — к 50 уровню на один левел-ап уходило больше года, к 70 — годы жизни, к 100 — сотни лет. Подробный разбор с таблицей цифр — см. историю чата, здесь только итоговые формулы.

**Кривая опыта** (`getExpToNext`) — заменена на линейную: `150 × уровень`. Откалибровано симуляцией: ~375 дней (~1 год) до 100 уровня при 100% ежедневной дисциплине, ~1100+ дней (~3 года) при выполнении примерно трети дней. Долгосрочно (за пределами 100 уровня) темп сам стабилизируется на ~5-6 днях за уровень и не взрывается повторно — это математическое следствие того, что награда (`getDynamicExp`) продолжает расти линейно с уровнем, а стоимость уровня теперь тоже линейна.

**Дневные цели** (`getDynamicTarget`, через `getTargetGrowthMultiplier`) — рост **без потолка** (сознательное решение — вдохновлено идеей прогрессивной нагрузки, не должно "упираться в стену"), но в два неспешных темпа:
- 1-10 ур.: щадящая кривая новичка (`getBeginnerMultiplier`, 0.5×→1.0×) — без изменений.
- 10-100 ур.: `+1.4%` за уровень.
- 100+ ур.: `+0.7%` за уровень (вдвое медленнее — "для самых упорных").

Референсные значения (база: отжимания 100 / приседания 120 / подтягивания 40 / пресс 100 / шаги 10000):

| Уровень | Отжимания | Приседания | Подтягивания | Пресс | Шаги |
|---|---|---|---|---|---|
| 10 | 100 | 120 | 40 | 100 | 10 000 |
| 30 | 128 | 153 | 51 | 128 | 12 800 |
| 50 | 156 | 187 | 62 | 156 | 15 600 |
| 100 | 225 | 271 | 90 | 225 | 22 600 |
| 200 | 296 | 355 | 118 | 296 | 29 600 |

**Награда за задание** (`getDynamicExp`) — намеренно **не менялась**, продолжает расти как раньше (`+5%/уровень`, без потолка, плюс бонусы от INT/титулов). Это математически необходимо для того, чтобы кривая опыта не взорвалась повторно на высоких уровнях (см. выше).

**Штраф и STR — "Вариант Б".** Раньше штраф почти обнулялся уже к 50 уровню независимо от вложений в STR (снижение от уровня само по себе пробивало минимальный порог в 1%). Теперь:
- Снижение от уровня: `⌊уровень÷20⌋ × 3%` (было `÷10` — вдвое медленнее).
- Снижение от STR: `0.25%` за очко выше 10 (было `0.5%` — вдвое медленнее).
- Минимальный порог: **5%** (было 1%).
Формула продублирована в двух местах — `applyPenaltyLogic()` (реальный штраф) и в служебной панели (блок `SL:SYS-TOOLS`, сейчас `applyPenaltyAction()`) — держать в синхроне при любых будущих правках баланса.

**INT и AGI** — сознательно не трогались в этой сборке (INT ускоряет прокачку опыта при вложении, AGI даёт шанс крита по кредитам — оба воспринимаются как осмысленные бонусы за вложение, а не системная дыра, в отличие от STR/штрафа).

В обычные дни (не первый запуск) `finishInit()` вызывается сразу, без задержки — там нет модалки, с которой можно столкнуться.
- **Смягчение уровней 1-2** — `getExpToNext()` использует ручные пороги для первых двух уровней вместо общей формулы `150×уровень`: 1→2 = 1000 опыта, 2→3 = 1500 опыта. С 3 уровня — без изменений. Теперь: 2 уровень — день 2, 3 уровень (и разблокировка Лимита) — день 5, при ежедневном 100% выполнении.
- **Уточнение по темпу «3 года» до 100 уровня** (из обсуждения, важно помнить при следующих правках баланса): это не «выполнение 1 дня из 3», как считалось изначально при грубой прикидке — с учётom реального штрафа за пропуски (который не просто не даёт опыт, а ещё и списывает уже накопленный) это соответствует темпу **«через день» (50% дней)**. Более редкое выполнение (раз в 3-4 дня) при текущих формулах даёт кратно больше 3 лет вплоть до полного застревания прогресса — это осознанно принято как честный эффект работы штрафа, не баг.

**v5.9.61 — исправлено накопленное расхождение между визуальным таймером сброса и реальным моментом сброса данных.**

**Найдено пользователем.** Живое наблюдение за моментом сброса: экранный таймер обнулился, но счётчики упражнений не сбросились и штраф не начислился — сработало только позже, примерно через минуту, при пробуждении экрана после сна.

**Диагностика заняла несколько заходов.** Первая версия (сдвиг из-за перехода на летнее время) отклонена — проверено поиском: Казахстан не переходит на летнее время с 2005 года, круглый год фиксированный UTC+5. Вторая версия (сбой обработчика пробуждения экрана) тоже отклонена — код `visibilitychange` уже корректно вызывает `checkMissedDays()` первым делом. Настоящая причина найдена при третьем заходе, после того как пользователь лично, вживую пронаблюдал точную последовательность событий (таймер обнулился → **ничего** не произошло даже спустя время → только после сна/пробуждения экрана сработало правильно).

**Реальная причина.** Визуальный таймер (`getNextResetTime()`) и реальный порог сброса данных (`checkMissedDays()`, через `data.lastReset + 86400000`) — два независимых расчёта. Первый **каждый раз пересчитывается заново**, от текущего момента, без всякой памяти о прошлом — поэтому никогда не накапливает ошибку. Второй **прибавляет фиксированное число миллисекунд к уже сохранённому прошлому значению** — если это значение хоть раз, когда-либо, оказалось не точно в 5:00:00.000 (по любой исторической причине) — каждое следующее «плюс ровно сутки» **переносит** то же самое смещение вперёд, никогда не исправляя его, потому что не сверяется ни с чем внешним, только с самим собой.

**Исправление.** Новая функция `getNextCleanReset(afterTimestamp)` — пересчитывает ближайшие чистые 5:00:00.000 **после** переданного момента, тем же принципом, что и уже существующая `getLastResetThreshold()`, но в противоположном направлении (вперёд, не назад). Обе точки расчёта внутри `checkMissedDays()` (`let nextReset = ...` и `nextReset += 86400000` внутри цикла) заменены на вызов новой функции — каждый шаг самокорректируется, а не наследует смещение от предыдущего.

**Важно, что логика многодневного пропуска не тронута** — цикл `while` по-прежнему обрабатывает каждый пропущенный день по отдельности (штраф за каждый день отдельно), не «перепрыгивая» сразу к сегодня.

**Проверено:** синтаксис — чисто; порядок операций внутри цикла подтверждён (`data.lastReset` обновляется раньше, чем пересчитывается следующий порог); симуляция трёх сценариев — (1) точное воспроизведение бага пользователя (смещение на 3 минуты) — теперь исправляется мгновенно, за один цикл, а не требует минутного ожидания; (2) обычный сброс без смещения — работает как раньше; (3) три пропущенных дня подряд — по-прежнему корректно обрабатываются по одному, ни один день не проглатывается разом.

Уведомления показываются по одному, через очередь (`notificationQueue`/`notificationActive`) — если к моменту постановки в очередь уже показывается другое уведомление (например, «Достигнут N-й уровень», у которого похожая задержка ~4500мс), показ откладывается на несколько секунд, а звук уже отыграл раньше, не совпадая с реальным появлением попапа. Оба вызова напоминания о сохранении переданы через `showNotice(..., 'danger', false, 'saveReminder')`, без отдельного ручного `playSound()` в `setTimeout`.

**Проверено:** синтаксис — чисто; построчный просмотр всех ~21 вызовов `showNotice()` с третьим аргументом `true`/`false` подтвердил — ни у одного из них нет четвёртого аргумента, случайно оставшегося от старой булевой схемы `skipSound`, все корректно продолжат работать по старому правилу «звук по тону»; симуляция очереди (уведомление о левел-апе уже показывается, следом ставится в очередь напоминание о сохранении) подтвердила — звук `saveReminder` теперь звучит именно в момент реального появления второго попапа на экране, не раньше.

**Проверено:** синтаксис — чисто; построчный просмотр **всех** вызовов `showNotice()` с тоном `warn`/`danger` подтвердил, что только 2 из более чем 25 таких вызовов получили `skipSound: true` — ни один другой отказ/предупреждение не пострадал случайно; симуляция трёх сценариев (напоминание о сохранении / настоящий отказ типа «Недостаточно кредитов» / событие Аномалии) подтвердила: только у напоминания о сохранении звук `denied` не играет, при этом запись в журнал у него сохранилась, а у двух контрольных сценариев (отказ и Аномалия) поведение звука и журнала осталось полностью прежним.

```js
if (isFreshInstall) { showRulesOverlay('onboarding'); }         // было
if (!data.rulesAcknowledged) { showRulesOverlay('onboarding'); } // стало
```

Только в третьем сценарии игра начинается сразу — в первых двух корректно проходит все три шага по порядку, включая тот самый баговый случай.

**v5.9.31 — крупный пересчёт баланса ранней прокачки: новая формула опыта до 10 уровня + базовый лимит Преодоления предела снижен до 1 раза в сутки.**

**Как обнаружилась проблема.** Пользователь достиг 3 уровня и заметил, что до следующего требуется всего 450 опыта (`150×3` по старой формуле) — «крайне мало». **Ключевая находка по Пределу — дело не в Выносливости.** Изначально предполагали, что разгон темпа связан с бонусом Выносливости в этом режиме — проверили отдельно и оказалось, что даже **без единого очка**, вложенного в этот стат, один раунд Предела **удваивает** дневной опыт (×2.00 ровно) — просто потому что `getDynamicExp()` не делает разницы между первым и повторным прохождением дня, начисляя одинаковую награду за каждое выполнение. Бонус Выносливости добавляет сверху совсем немного (×2.03 вместо ×2.00).

**Решение по Пределу (сознательное, не техническая правка бага).** Опыт за раунд Предела **не трогали** — по прямому решению пользователя это справедливая награда за реально выполненную работу. Вместо этого — **сам базовый лимит использований снижен с 2 до 1 раза в сутки** (`getDailyLimitBreakCap()`: `cap=2`→`cap=1`, бонусы от артефакта Печать Предела и расходников по-прежнему добавляются сверху). Больше одного раунда в день теперь возможно только через отдельно заработанные/купленные предметы, не бесплатно по умолчанию.

**Формула опыта до 10 уровня переписана с нуля, дважды с первого захода не получилось.** Первая попытка (снижающийся коэффициент от 600× к 150×, точка перехода 10-20 уровень) провалила собственную же проверку — оказалось, что при слишком резком снижении коэффициента итоговое требуемое число опыта могло **падать** на некоторых уровнях внутри диапазона перехода, нарушая условие «растёт всегда». Вторая попытка (добавка поверх растущей линейной базы, а не убывающий коэффициент) уже гарантировала монотонный рост математически — но при попытке точно попасть в `150×10=1500` ровно на границе 10 уровня выяснилось, что для короткого окна (7 шагов, уровни 3-10) физически нет места для сколько-нибудь заметной "щадящей" надбавки: любое значение выше ~1500 на 3 уровне неизбежно потребовало бы **снижения** где-то по пути к 10-му, что запрещено. **Финальное, принятое пользователем решение** — отказаться от сложной "надбавки, убывающей к линейной формуле" в пользу простой арифметической прогрессии:

```js
function getExpToNext(lvl) {
  if (lvl <= 9) return 1000 + 50 * (lvl - 1);
  return Math.floor(150 * lvl);
}
```

Уровни 1-9: 1000, 1050, 1100, ..., 1400 (шаг +50 за уровень, всегда монотонно). С 10 уровня — обычные `150×уровень`, без изменений от прежней формулы. Единственный чуть более крупный шаг — на самой границе (9→10 уровень: +100 вместо +50), но он всё равно растущий, не проблема сам по себе.

**Проверенный результат по темпу** (без использования Предела): 3 уровень — 4 дня, 10 уровень — 18 дней, 100 уровень — **382 дня**, что очень близко к исходной, давно откалиброванной цели (~375 дней). Формула опыта проверена на монотонность программно (не на глаз) — прогнана через ту же самую функцию, что и в реальном коде, не через отдельную копию для теста.

**Глава Кодекса «Преодоление Предела»** — «до двух раз в сутки… сверх плана» → «раз в сутки… может продолжить выполнение» (заодно убрано слово «плана» — было решено ранее избегать этого слова в тексте).

**v5.9.21 — исправлен момент срабатывания триггера Преодоления предела (в той же сессии, до заливки v5.9.20 на GitHub).**

**Пользователь поймал неточность в понимании самой механики Преодоления предела.** Я дважды описал её неверно в двух разных формулировках подряд, прежде чем разобрался в реальном коде: это не "открытый режим, где можно свободно закрывать задания сколько угодно", а **дискретное, ограниченное действие** — кнопка доступна только после закрытия всех 5 обычных заданий, нажатие обнуляет прогресс и запускает **один конкретный раунд** повторного прохождения тех же 5 заданий (с удвоенной наградой), после которого нужно нажать кнопку заново для следующего раунда (если есть ещё использования).

**Триггер шкатулки перенесён с момента нажатия кнопки на момент завершения раунда.** Было: `Math.random() < 0.05` прямо в обработчике клика по кнопке (до того, как раунд вообще начался). Стало: новый флаг `data.limitBreakRoundPending` — выставляется в `true` при нажатии кнопки (вместо старого сразу-броска), а сам бросок 5% происходит в обработчике клика по заданию, **переиспользуя уже существующую переменную `wasAllDone`** (она и так уже вычислялась там для другой цели — определения момента первого закрытия всех заданий за день, до вызова `checkLevelUp()`): `if (data.limitBreakRoundPending && wasAllDone) { ...roll...; data.limitBreakRoundPending = false; }`.

**Приятный побочный эффект** — раз бросок больше не в обработчике кнопки (который делает `location.reload()` сразу после), а в обработчике клика по заданию (который `reload()` не делает вообще) — весь механизм `data.pendingAnomalyNotice` из v5.9.20 (флаг + проверка в `finishInit()` после перезагрузки) оказался **не нужен и полностью убран**: обычный `setTimeout(...,4500)` теперь просто работает напрямую, без обходных путей.

**Защита от утечки между днями:** если раунд был начат (`limitBreakRoundPending = true`), но не завершён до суточного сброса (игрок не доиграл до конца дня) — флаг явно сбрасывается в `checkMissedDays()`, иначе он мог бы ложно сработать на следующий день при закрытии обычных, никак не связанных с Преодолением предела заданий.

Проверено симуляцией трёх сценариев: (1) обычное закрытие дня без активного раунда — бросок не срабатывает; (2) активация → 4 из 5 заданий раунда закрыто — бросок ещё не срабатывает; 5-е закрыто — срабатывает ровно один раз; (3) повторные закрытия после этого — не срабатывают снова.

**v5.9.20 — Шкатулка Аномалии, 49-я и последняя иконка.**

Новый 9-й тип шкатулки, **полностью вне** обычной системы тиров/весов/лут-таблиц — сознательно, по замыслу с самого начала обсуждения.

**`box_anomaly` в `BOX_CATALOG`** — только `name`/`icon`/`desc`/`level:3`, без `weight`/`minItems`/`maxItems`/лут-полей (они и не нужны, у неё своя отдельная логика открытия). **`getAvailableBoxTiers()` явно исключает `box_anomaly`** — иначе она случайно попала бы в обычный `rollBoxTier()` наравне с прочими тирами.

**Два независимых триггера получения, не связанных с обычной системой шкатулок:**
- **8%** дополнительно при каждом левел-апе (от 3 уровня), **сверх** уже гарантированной обычной шкатулки — добавлено прямо в цикл `checkLevelUp()`, использует уже существующий механизм группировки/уведомлений для `gainedBoxes` (никакого отдельного кода для уведомления не потребовалось — сработало "бесплатно").
- **5%** при каждой активации «Преодоления предела» — **технический нюанс**: обработчик кнопки вызывает `location.reload()` сразу после `saveData()`, так что `setTimeout` там никогда не успел бы сработать. Решение — флаг `data.pendingAnomalyNotice`, проверяется и показывается в `finishInit()` **после** перезагрузки страницы, с задержкой в 1с.

**Открытие — отдельная функция `performOpenAnomalyBox()`, не через общий `performOpenBox()`.** Один бросок 50/50:
- **Проклятие (50%)** — `data.pendingCurse = true`, применяется **не сегодня, а завтра**: при следующем суточном сбросе `checkMissedDays()` переносит `pendingCurse` → `curseActiveToday` (та же строка, что и сброс `dailyTargetLevel`), действует ровно один день, затем `checkMissedDays()` автоматически выставляет `curseActiveToday` в `false` на следующем сбросе (просто присваивая значение из уже сброшенного `pendingCurse`, а не отдельным явным сбросом). `getDynamicTarget()` применяет `×1.40` **поверх** уже применённой скидки от рун/Выносливости (не вместо неё) — `Math.ceil` вместо `Math.floor`, чтобы округление работало в пользу Системы, а не игрока (та же логика наоборот, что у скидок).
- **Благословение (50%)** — три категории: **40% ключ** (Алый/Багровый/Пурпурный/Теней, с защитой от дублей — если уже есть все 4, честно откатывается на кредиты вместо пустого результата), **30% кредиты** (плавающая формула `500 + 30×уровень`, потолок 8000 — специально ниже максимума Шкатулки Теней в 10000, чтобы та оставалась самой щедрой шкатулкой в игре), **30% случайный усиленный расходник** (из уже существующих шести).

**Восприятие сознательно не участвует** ни в шансе получения, ни в исходе открытия — единственная полностью статонезависимая механика в игре, по прямому решению пользователя (чтобы сохранить настоящий, неконтролируемый риск).

**Иконка `box_anomaly.png`** — обработана тем же методом "на просвет", что и остальные 48 (пользователь загружал с однородным чёрным фоном, как и раньше). **Это была последняя из запланированных иконок — теперь все 49 используются кодом.**

Проверено полной симуляцией (не вручную): исключение из обычных тиров на разных уровнях, математика проклятия (с скидкой и без), защита от дублей ключей, значения плавающей формулы кредитов на 8 разных уровнях — всё сошлось с расчётами, которые обсуждались в чате.

**Кодекс** — глава «Шкатулки» дополнена (не создавалась отдельная глава — по аналогии с тем, что и остальные 8 тиров шкатулок не имеют собственных глав, только общая).

**Часть B — ключ-защита входа в служебную панель (по стороннему ТЗ).** Раньше 7 тапов по версии в Архиве сразу открывали «Длань архитектора». Теперь между тапами и панелью встала модалка авторизации:
- **Новая модалка** `#sysToolsAuthOverlay` (`z-index:1600` — выше Архива и обычных confirm-окон, чтобы гарантированно оказаться поверх) — заголовок «АВТОРИЗАЦИЯ», текст «Обнаружен запрос к служебному контуру. - **Проверка ключа** — `sha256Hex(SYS_TOOLS_SALT + trim(введённое))` через нативный `crypto.subtle.digest('SHA-256', ...)` (без внешних библиотек), сравнение с константой-хэшем. **Пароль в открытом виде нигде в коде не хранится** — только соль (`SYS_TOOLS_SALT = 'SL:ARCH:2026'`) и итоговый хэш (`SYS_TOOLS_KEY`). - Закрытие — только «Отмена» или успешный ввод, **без** клика по фону (сознательно, по аналогии с остальными модалками, где есть поле ввода — `confirmOverlay`/`nameOverlay` тоже не закрываются кликом по фону, чтобы случайный тап мимо поля не сбрасывал набранное).
- Весь новый код (HTML модалки, JS-логика, константы) — внутри уже существующих маркеров `SL:SYS-TOOLS`. `#itemPreviewOverlay` не тронут. Имя `openSysTools()` и остальной API панели не менялись.

**Если пароль когда-нибудь понадобится сменить** — посчитать новый хэш той же формулой (`SHA-256(SYS_TOOLS_SALT + новый_пароль)`, например через `crypto.subtle.digest` в консоли браузера или через `node:crypto`) и заменить константу `SYS_TOOLS_KEY` — больше нигде в коде пароль не хранится и трогать не нужно.

**v5.9.15 — по итогам стороннего code review: устранение риска рассинхрона формулы штрафа + текстовые правки.**

**Формула штрафа сведена к единственной копии.** Новая функция `computePenaltyAndApply()` — вся математика (`basePen`/`lvlReduction`/`strReduction`/`finalPen`/`loss`/`shortfall`/`expDebt`) и мутация данных теперь существуют **в одном месте**. `applyPenaltyLogic()` (реальный суточный штраф) стал тонкой обёрткой — проверяет условия (`isGoalMet`/`allQuestsDone`) и, если применимо, просто вызывает общую функцию. `applyPenaltyAction()` (кнопка «Применить штраф сейчас» в «Длани архитектора») — тоже просто вызывает её напрямую, без гейтинга (тестовая кнопка обязана срабатывать всегда). **v5.9.14 — долг по штрафам, заморозка дневных целей, формулировки рун очищения.**

**Обнаруженная и закрытая дыра в балансе.** Раньше `data.exp = Math.max(0, data.exp - loss)` — если штраф "хотел" снять больше опыта, чем было накоплено, недостача просто пропадала бесследно, а не терялась частично. Проверили симуляцией: раз опыт после штрафа тоже никогда не уходит в минус, попав в состояние "опыт = 0" (например, сразу после левел-апа) — игрок мог пропускать дни **сколько угодно** без единой реальной потери опыта, пока сам не решит вернуться к тренировкам. Единственные последствия в этом состоянии — счётчик `totalPenalties` и сброс серии, оба второстепенные по сравнению с потерей опыта.

**Решение — «долг перед Системой» (`data.expDebt`).** Если штраф превышает доступный опыт — недостача (`shortfall = max(0, loss - data.exp)`) записывается в `data.expDebt`, а не пропадает. Новая функция `gainExp(amount)` — единая точка входа для **любого** начисления опыта в игре (награда за задание, восстановление после штрафа, пополнение через «Длань архитектора» — всего 8 точек вызова переведены на неё, ни одного `data.exp +=` не осталось нигде, кроме самой этой функции): сначала гасит долг, и только остаток (если есть) реально добавляется к `data.exp` и может вызвать левел-ап. Пока долг не закрыт — видимого прогресса на шкале опыта не будет, даже при регулярном выполнении заданий.

**Отображение долга** — новая строка в шапке `#expDebtLine` (внутри `.rank-info`, сразу под «EXP: X / Y»), физически скрыта (`display:none`) и появляется только когда `data.expDebt > 0`, текст «Долг перед Системой: −N EXP». Сама строка «EXP: X / Y» дополнительно получает класс `.exp-in-debt` (красный `#ff5555` с тем же свечением, что у баннера штрафа) на время действия долга — оба визуальных сигнала управляются в `render()`.

**Глава Кодекса «Наказание за Слабость»** дополнена четвёртым предложением про долг, порядок предложений — по финальной правке пользователя (смягчение силой/уровнем — сразу после первого предложения, долг — перед заключительным «Система не прощает бездействия», а не после).

**«Заморозка» дневных целей по уровню на начало суток.** Новое поле `data.dailyTargetLevel` — устанавливается один раз при суточном сбросе (`checkMissedDays()`), равно уровню игрока на этот момент. **4 места**, где раньше цель считалась по живому `data.level`, переведены на `data.dailyTargetLevel`: отображение/разблокировка кнопки «+» на задании (`render()`), проверка «всё выполнено сегодня» (`allQuestsDone()`, `countDoneQuests()` — используются штрафом, Преодолением предела, уведомлением «Выполнено», процентом дня). Порядок в `checkMissedDays()` важен: `donePercent` для **завершающегося** дня снимается **до** обновления `dailyTargetLevel` на новый день — иначе день оценивался бы по целям следующего дня. Награда за опыт (`getDynamicExp`) намеренно не тронута — продолжает считаться по живому уровню, левел-ап посреди дня по-прежнему сразу увеличивает награду, просто больше не увеличивает сами требования уже начатого дня.

**Синхронизация с «Длань архитектора»** — `addExpAction`, `quickExpAction`, `setLevelAction`, `quickLevelAction` дополнены строкой `data.dailyTargetLevel = data.level;`, иначе резкая смена уровня через панель тестирования показывала бы цели под старый, уже неактуальный уровень.

**Формулировки рун очищения** — избегаем и «не влияет на Летопись» (негативная конструкция), и голого «Снижает счётчик...» (слишком похоже на интерфейсный, не системный текст). Финальный вариант — через «память Системы»:
- Руна Очищения: «Стирает 1 штраф из памяти Системы.»
- Руна Полного Очищения: «Стирает 5 штрафов из памяти Системы.»
- Руна Очищения Судьбы: «Стирает 3 штрафа из памяти Системы и возвращает 3× последнюю известную потерю опыта.»
Руна Исправления не тронута — единственный предмет, который по-настоящему переписывает Летопись, в этом и есть её уникальность.

**Пойманный и исправленный баг (в той же сборке, до заливки на GitHub).** Пользователь протестировал на своём компьютере: применение штрафа снимало опыт до нуля, но долг никогда не появлялся, сколько раз штраф ни применялся. Причина — забыл продублировать логику долга (`shortfall`/`expDebt`) во **второй** копии формулы штрафа, в `applyPenaltyAction()` (кнопка «Применить штраф сейчас» в «Длани архитектора») — обновил только «настоящую» `applyPenaltyLogic()`. **v5.9.10 — Выносливость получила постоянный эффект (не только в Преодолении лимита).**

Пользователь заметил дисбаланс: из пяти статов только Выносливость работала **исключительно** в опциональном режиме (Преодоление лимита) — если игрок им не пользуется, вложенные очки ничего не давали, в отличие от остальных четырёх статов, полезных всегда. Решение — добавить второй, постоянный эффект поверх уже существующего бонуса в Лимите.

**`getDynamicTarget()` переписана** — постоянное снижение целей заданий от Выносливости:
- `staReduction = min(0.20, bonusSta * 0.001)` — 0.1% за очко, потолок **20%**
- Складывается с уже существующим временным снижением от рун (`targetDiscountRate`, если активно) — но **сумма обоих не может превышать 60%** (`combinedReduction = min(0.60, staReduction + runeReduction)`)
- Ставка намеренно ниже, чем у остальных эффектов Выносливости/Восприятия (0.1% против 2%/0.3%) — снижение целей задания это не абстрактное число, а реальное количество повторений, раздавать его щедро означало бы обесценивать саму суть тренировочного приложения

Референсные цифры (подтягивания, база 40, уровень 30): без вложений — 51, при потолке Выносливости (нужно 200 очков сверх старта, STA=210) — 40, при потолке Выносливости **и** одновременно активной Руне Снятия Бремени — 20 (упирается в общий потолок 60%, а не в сумму 20%+45%=65%).

**Логика игрока, подтверждённая пользователем:** если хочется, наоборот, увеличить нагрузку сверх обычной — для этого уже существует «Преодоление лимита» (полностью добровольная опция). Обе механики не конфликтуют, а взаимно дополняют друг друга.

**Итоговая формула Выносливости:**
- Всегда: −0.1%/очко к целям заданий, потолок −20% (складывается с рунами, общий потолок −60%)
- В режиме «Преодоление лимита»: +2%/очко к опыту, без потолка (как в v5.9.9, не изменилось)

| Восприятие | `per` | PER | Тройной эффект на "удачу": вес редких тиров при розыгрыше шкатулки за левел-ап, шанс бонусных кредитов из шкатулки, смещение выбора внутри лут-таблицы шкатулки в сторону более редких/сильных позиций | +0.3% на все три сразу | нет |

**Реализация Выносливости** — в `getDynamicExp()`: `if (data.isGoalMet) mul += bonusSta * 0.02`. Проверено: не действует вне Лимита, только пока флаг `isGoalMet` истинен (тот же флаг, что уже даёт ×2 к кредитам в этом режиме).

**Реализация Восприятия** — три места:
1. `rollBoxTier()` — веса всех тиров **кроме** Базальтовой/Ониксовой (сознательно оставлены как "гарантированный пол") умножаются на `(1 + bonusPer*0.003)`.
2. `performOpenBox()` — `effectiveCreditChance = box.creditChance + bonusPer*0.003`.
3. `performOpenBox()` — новая функция `pickFromPool(arr)`: с вероятностью `bonusPer*0.003` выбирает предмет из "второй половины" массива лут-таблицы вместо равномерного выбора по всему массиву. **Важная оговорка** — это приближение, не честная система рангов силы предмета: массивы `BOX_LOOT_POOLS` были составлены по общему принципу "слабее → сильнее", но не проверялись строго на этот счёт. Если понадобится более честная механика — стоит переписать лут-таблицы на явные объекты с полем "сила/редкость" вместо массивов-с-повторами.

## UI/UX-конвенции, которые важно соблюдать

- **Никаких нативных `alert()`/`confirm()`/`prompt()`** — всё оформлено как стилизованные модалки/баннеры в духе «системных окон» (см. `.status-overlay`, `.system-popup`, `showConfirm()`, `showNotice()`). Если добавляешь новое действие, требующее подтверждения или показывающее результат — используй существующие хелперы, не откатывайся на браузерные диалоги.
- **HUD-эстетика**: тёмная сине-чёрная палитра, шрифт Orbitron для заголовков/лейблов, тонкие голубые угловые «скобки» (`.hud-frame`) на панелях и модалках, приглушённая сетка-текстура на фоне панелей. Золотой цвет зарезервирован под системные объявления (левел-ап, титулы, ранги), не под рутинные элементы.
- **Аккуратно с анимациями** — `@keyframes` (`levelUp`, `completeText`, `flash`, `pulse-bg/text`, `auraPulseSss/Monarch`, `systemPopupIn`) не трогать без явного запроса; в паре версий явно проверялось, что правки логики их не задевают.
- Красный/danger-стиль (`.danger-*` классы) зарезервирован под реально необратимые или предупреждающие действия (сброс прогресса, ошибки). Не использовать для рутинных сообщений.

## Рабочий процесс с пользователем (важно!)

Пользователь **не программист**. Установленное явно правило по ходу разработки: **не писать код без прямой команды пользователя** — сначала обсуждение, план, уточняющие вопросы (что не мешает, а что можно менять — например, дизайн/анимации трогать нельзя без явного разрешения), и только после явного «пиши код» — правки. Это правило нарушалось один раз и было явно зафиксировано пользователем как недопустимое — при работе через Claude Code стоит придерживаться той же логики: сначала план и confirmation, потом implementation, особенно для нетривиальных изменений (баланс, новые механики, структурные правки). Мелкие explicit-командные правки («сделай имя жирным», «сократи до SLDT») можно делать сразу.

При любых изменениях **всегда объяснять пользователю простыми словами**, что и почему меняется — он не разбирается в коде и оценивает результат только по итоговому поведению приложения.
