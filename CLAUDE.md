# CLAUDE.md

Контекст проекта для Claude Code. Прочитай этот файл перед началом работы.

## Что это за проект

Solo Leveling Daily Training (SLDT) — локальный фитнес-трекер ежедневных заданий в визуальной стилистике манхвы/аниме Solo Leveling. Это **трекер с игровыми элементами**, а не игра с элементами трекера — важное разграничение, зафиксированное с пользователем явно: никаких виртуальных событий (подземелья, врата, битвы с монстрами и т.п.), только реальные упражнения (отжимания, приседания, подтягивания, пресс, шаги) с игровой надстройкой (уровни, ранги, титулы, артефакты, магазин).

Репозиторий на GitHub: `solo-leveling-tracker`.
Текущая версия: **v7.5.10**.
История версий (записи по версиям, что и почему сделано) — в `CHANGELOG.md`; здесь — только правила.

**ПРАВИЛО (с v5.9.54): все цены новых предметов должны быть чётными числами** — чтобы продажа за 50% всегда давала целое число без необходимости полагаться на `Math.floor()` как единственную защиту.

Папка `screenshots/` лежит только в репозитории: в архив версии её не класть (решение пользователя), Service Worker её не кэширует. Картинка — шесть экранов 7.3.2 (пересобрана по просьбе пользователя после v7.3.2; сборщик `/home/claude/v7/s20b.py` — ждёт 3,5 с, пока проявятся нити в полосах); пересобирать только по просьбе пользователя.**

## Технологии и структура файлов

Никакого билд-процесса, фреймворков или npm-зависимостей. Чистый HTML/CSS/JS.

```
index.html      — всё приложение: разметка, стили (<style>), логика (<script>) в одном файле
manifest.json   — PWA-манифест
sw.js           — Service Worker (кэширует приложение + иконки + шрифт Orbitron для офлайна)
icons/          — иконки приложения (сгенерированы из исходного логотипа, разные размеры/назначения)
CHANGELOG.md    — история версий (от новых к старым); CLAUDE.md — правила, README.md — описание для игроков
```

Все данные пользователя хранятся в `localStorage` (два ключа: состояние прогресса и суммарная статистика за всё время). Никакого бэкенда, никакой синхронизации между устройствами — экспорт/импорт прогресса через файл `.json` или код в буфере обмена (обе опции живут в модалке «АРХИВ»).

## Версионирование и совместимость сохранений

- Номер версии указан в `<title>` и в `#limitBreakContainer`/шапке — держи его синхронизированным при правках.
- Ключи `localStorage` версионируются (`sl_daily_vX_Y_Z`, `sl_total_stats_vX_Y_Z`). Список `PREV_KEYS`/`PREV_STATS_KEYS` в начале скрипта — цепочка миграции старых сохранений на новый ключ.
- **Бампать ключ хранения нужно только при изменении структуры данных**, а не при чисто косметических/визуальных правках — иначе накапливается мусор миграций. Чисто CSS/текстовые правки (примеры — v5.5.1–v5.5.7) номер ключа не меняли.
- При добавлении нового поля в объект `data`: обязательно добавить его (а) в дефолт для чистой установки, (б) в блок миграции старых сохранений с фолбэком, (в) в защитную нормализацию сразу после загрузки (на случай кривых/старых данных), (г) в `sanitizeImportedData()` для валидации при импорте бэкапа.
- **Шрифты (правило с v6.6.6): текст — `'Exo 2 Text'` (400, жирное 700, размер +8% к прежнему моноширинному); игровые числа — Orbitron (счётчики, цели, награды, кнопки «+», уровень, таймер, опыт/кредиты/серия, характеристики, цены); служебные числа — Roboto Mono (время записи в журнале, даты календаря Летописи, номер версии); заголовки, кнопки, названия упражнений — `'Orbitron', 'Exo 2'`.** `'Exo 2 Text'` — отдельное имя семейства намеренно: если добавить начертание 400 в `'Exo 2'`, заголовки и кнопки взяли бы его вместо 500 и стали бы тоньше. Новые текстовые элементы подключать к блоку «v6.5.36: основной текст» в конце `<style>`.
- **Счётчики времени (с v6.6.0): каждая цифра — в ячейке одинаковой ширины** (`.tbox .tc.dg` 0.78em, двоеточие `.col` 0.34em), группа ячеек — в контейнере у правого края. У Orbitron цифры разной ширины, и без ячеек время «скачет» каждую секунду. Обновлять только изменившиеся ячейки (`renderTimerCells`). Новые счётчики времени делать так же.
- **Анимации с `transform` (с v6.6.7): если элемент центрирован через `transform: translate(...)`, а анимация тоже задаёт `transform`, центрирующий сдвиг обязан быть в каждом кадре** — иначе кадры его затирают и элемент уезжает (так было у LEVEL UP до v6.5.36 и у «COMPLETE» до v6.6.7). С v7.3.4 надпись LEVEL UP центрируется флексом (`.lvx`), сдвиг в кадрах не нужен.
- **Кредиты на экране (с v6.6.10): «◈» в текстах кода — это метка, а не символ для показа.** Любой текст с кредитами выводить только через `creditsHtml(text)` (экранирует, затем заменяет метку постоянной разметкой значка `CREDIT_ICON_HTML` — векторный образец `#credSeal` в начале `<body>`). Не выводить «◈» через `textContent` и не вставлять значок до экранирования.
- **Терминология (с v6.6.11):** «увеличение получаемого опыта / получаемых кредитов», а не «усиление опыта/кредитов» (пользователь: «усиление кредитов» безграмотно — увеличиваются начисляемые, а не накопленные). **Сумма кредитов — всегда значком (метка «◈»), слово «кредиты» — только без суммы** («Недостаточно кредитов.»); значок заодно снимает проблему склонения («1 кредит / 2 кредита»).
- **Панель активных эффектов (с v6.8.2):** порядок — временные → титул → снаряжённые артефакты (в порядке контуров); одна строка с прокруткой вбок без полос прокрутки, затухание 26px по краям (справа — пока правее скрытое, слева — после сдвига), запас 12/10px под подсветку/разряд/искры; точки 7px справа снизу — голубая у артефакта, зелёная у активного титула; подробности артефакта «Артефакт: …» + эффект без приставки (`artifactEffectText`).
- **Знаки в панели активных эффектов (с v6.6.12):** искры — эффект **ожидает** (с v7.1.10 каждое кольцо стартует со своего места на круге — отрицательная `animation-delay` с шагом 0,618 оборота по номеру кольца в ряду; скорость у всех 0,84 с) (три — Бремя Аномалии, одна — ожидающие свитки и «спящие» руны); бегущий разряд — **руна работает**; ничего — руна подавлена Бременем или эффект не руна. (Ошибка при обсуждении: я утверждал, что у работающих рун «три искры» — неверно, пользователь поправил.)
- **Артефакты действуют только в снаряжении (с v6.7.0):** эффект любого артефакта проверять через `isArtifactEquipped(id)`, никогда через `data.inventory.includes(id)` (наличие в Инвентаре — только для выдачи и показа). Словарь (с v6.8.5): **«Контур снаряжения» — вся секция, одна на Игрока** (заголовок «КОНТУР СНАРЯЖЕНИЯ»); отдельные ячейки в текстах **не называются** — говорится о вместимости («Вместимость контура снаряжения увеличена.») и заполненности («Контур снаряжения заполнен.»); действия «снарядить» / «извлечь», артефакт «размещён в контуре снаряжения». Не «ячейка», не «слот», не «контуры» во множественном числе. Уровни открытия контуров (`CONTOUR_LEVELS` = 10/30/50/70) **нигде в текстах не упоминаются** — сюрприз.
- **Контроль темпа (с v6.8.0):** любое новое место, где игрок вносит повторения кнопками, проверять через `paceAllows(id, val)` и (с v7.4.0) после засчитывания вызывать `fzAdd(id, val)` — шкала усталости; инструменты Длани контролем не ограничены. Числа (подходы 60/80/40/60, окно 2 мин, запас 2 подхода) нигде в текстах не называются.
- **Именование предметов (с v6.8.3):** сильная версия — прилагательным перед вторым словом («Руна Надёжной Защиты», «Руна Абсолютной Защиты», «Зелье Полного Восстановления»); если обычной версии нет — без приставки («Руна Роста», «Руна Восстановления»); **без числительных** и без «(усиленная)». Названия меняются только в каталоге и `ITEM_GENITIVE` — внутренние коды предметов (`*_charged`, `shard_limit_double`) не трогать: на них держатся сохранения.
- **Свиток Отречения (с v6.8.4) отключает все дневные преимущества сборки:** Интеллект, Ловкость, Выносливость, **Силу** (в штрафе), бонусы титула, Кристалл Прозрения, Кристалл Ускорения, Амулет Непрерывности, **Кристалл Теней** (опыт, кредиты, шкатулка), **Амулет Воли**. Не отключает: Печать Предела (Преодоление — не прибавка к награде), очки характеристик при повышении уровня (рост, не дневное преимущество). Новый дневной эффект артефакта/характеристики — сразу решать, подпадает ли под Отречение (`RENUNCIATION_SUPPRESSED_ARTIFACTS`).
- **Новые стили — в конец `<style>` (с v6.9.0)**, после базовых правил: тестовый браузер (jsdom) применяет правила по порядку, игнорируя специфичность, — правило-уточнение, стоящее выше базового, в тестах «проигрывает» (случаи v6.8.2 и v6.9.0). Настоящие браузеры выбирают по специфичности, но держать порядок «база → уточнения» надёжнее везде.
- **Эффекты поверх элементов, которые перерисовываются** (счётчик упражнения и т. п.), запускать **после** перерисовки (`setTimeout(…, 0)`), иначе перерисовка сотрёт добавленные слои (v6.9.0: сбой числа под Бременем).
- **Новый статус дня в Летописи** — сразу: цвет `.day-cell.<статус>`, пункт в «Обозначениях» (`#legendBody`) того же цвета, слово в итогах месяца, `VALID_STATUSES` бэкапа. Проверка LG1 сверяет статусы бэкапа с легендой и упадёт, если пункт забыт (так было с Заморозкой до v6.9.1).
- **Тексты Костяной бусины и Пелены покоя — только в `VEIL_TEXTS`** (одно место, ради будущего перевода на английский: «Пелена покоя» → Veil of Rest). Название эффекта в текстах — в именительном падеже, после слова «эффект» — в кавычках («эффект «Пелена покоя»»). В панели эффектов название — **по предмету** («Костяная бусина»), эффект — в описании.
- **Стенд Service Worker** грузит иконки по очереди с задержкой 2 с на каждую — идёт ~2,5 мин (не зависание); каждая новая иконка в кэше добавляет 2 с. Наборы запускать по отдельности, общий `npm test` может не уложиться в лимит инструмента.
- **Бэкап (с v6.10.3)** — только через `buildSignedBackupCode()` (экспорт и файла `.slbackup`, и кода) и `parseBackupText()` (импорт и файла, и кода). Подпись защищает только файл/код бэкапа — не Реестр: туда приложение отправляет данные напрямую. Base64 — кодировка, не шифр; подпись лежит в открытом коде — защита от правки «в блокноте» и неаккуратной подделки, не от упорного человека (решение пользователя: достаточно).
- **В тестах (jsdom) нет `TextEncoder`/`TextDecoder`** — подключать в окне (`w.TextEncoder = TextEncoder`), иначе бэкап-функции падают; в браузерах они есть всегда.
- **Свитки Договора, Переноса, Отречения — «сделки»** (принцип с v6.5.2x): усложняют день в обмен на что-то и не позволяют избежать последствий. Поэтому под Договором, Переносом и (с v7.2.0) Сосредоточением **спят** обычная и Надёжная Руны Защиты, Руна Снятия Бремени и Руна Освобождения (с v6.5.30–6.5.31): защита или облегчение поверх сделки отменяют её цену. Пример: налог Переноса ×1,3 на оставшиеся упражнения и Руна Снятия Бремени −25% дают ≈ 0,98 — пропуск упражнения при нагрузке ниже обычной. Руна Абсолютной Защиты — исключение (отдельный дорогой уровень, без исключений). Пересмотрено пользователем в v6.10.6 — **оставлено как есть**. **С v7.2.3:** руна, использованная во время Пелены покоя, её следа или Заморозки, проверяется по тому, что ждёт её в первом обычном цикле: ожидающее Бремя Аномалии — отказ (руна защиты не тратится), свиток-«сделка» в очереди — предупреждение в окне подтверждения (`runeCarryHold`, `queuedDealGen`).
- **Дневные эффекты во время Пелены покоя и Заморозки (с v6.10.6)** — Зелье Роста, Руна Роста, Руна Возврата, Кристаллы Ясности и Импульса, Руны Освобождения и Снятия Бремени (`HOLD_EFFECT_GEN`): ждут окончания или досрочного снятия, показываются «(ожидает)» с искрой; расходники предела (`LIMIT_ITEM_ACC`) во время Пелены и Заморозки запрещены. Новый «держатель» дня без задания — добавлять в `dayEffectHold()`.
- **Версия 6.10.7 — стабильная точка отката** (решение пользователя перед сменой оформления): архив `solo-leveling-pwa-v6_10_7.zip`.
- **Две темы оформления (с v7.0.0):** `data.theme` — `'system'` («Система», основная, у всех по умолчанию) или `'classic'` («Классика», остаётся навсегда как выбор игрока; Архив → Настройки → «Оформление»). Проверка — только `isSysTheme()`. **Все стили темы «Система» — в блоке «ТЕМА «СИСТЕМА»» в конце `<style>`, каждое правило начинается с `body.theme-sys`** (тест T32 это проверяет) — в «Классике» ни одно из них не действует. **Правило пользователя (после v7.0.0): все будущие правки делаются в обеих темах** — новый элемент, состояние, окно или исправление должны быть оформлены и проверены снимками и в «Системе», и в «Классике»; правка только в одной теме — лишь по явному решению пользователя (так оставлены прежние прогресс-бары «Классики»: 4 / 4 / 3px против 3px у всех трёх в «Системе» — подтверждено пользователем). Уже существующий вид «Классики» без решения пользователя не меняется: он сверяется попиксельно с предыдущей версией (см. запись v7.0.0).
- **Окна в теме «Система» «одевает» модуль `SysTheme`** — на месте, при открытии (слежение за `style` оверлея): дети окна переносятся в `.sf-content > .sf-panel.mw`, заголовок — в табличку `.mw-hdr > .mw-tt`, рамку рисует `SysFrame.render(win, схема, SYS_FRAME_OPT)`; в «Классике» разметка возвращается к исходной. Поэтому: **код окон писать под классическую разметку и не рассчитывать, что элемент — прямой потомок `.status-window`** (в теме «Система» между ними две обёртки; пример — подсказка Летописи: отсчёт от `offsetParent`); новое окно — обычный `.status-overlay > .status-window` с `.status-header`, оно «оденется» само; значок «!» перед заголовком — только у запросов и уведомлений (`IC_ALWAYS` в `SysTheme`), у обычных окон его нет.
- **Общее правило кнопок темы (`body.theme-sys .sf-win.mwin button`) перекрывает классические правила состояний кнопок** — новое состояние кнопки (класс, который ставит код) нужно продублировать в блоке темы (так потерялся оранжевый «перегрев» `.pace-hot`, найдено снимками в 7.0.0). Правило темы «сброс наведения» (`button:hover` с `!important`) действует и на выключенные кнопки: у кнопки со своим видом недоступного состояния его нужно закрепить отдельно (кнопка Предела, v7.0.1). Цвет текста кнопки в теме — переменная `--bc`.
- **Длинные окна не пересобирать после действия (с v7.0.5):** если после нажатия меняется одна строка или одна карточка — обновлять её на месте, а не стирать и рисовать всё окно заново (`innerHTML` целиком). В теме «Система» окно — отдельный слой (`will-change`, v7.0.1); на телефоне полная перерисовка длинного слоя видна: окно пропадает целиком или кусками (каталог Длани, ≈50 карточек). ## Ключевые игровые системы (кратко, для ориентира)

- **Квесты**: 5 заданий в день (pushups/squats/pullups/press/steps), цель на день считается через `getDynamicTarget()` — растёт с уровнем, но с уровня 1 по 10 действует щадящий множитель (0.5×→1.0× линейно, `getBeginnerMultiplier()`), дальше — обычный рост. Награда (`getDynamicExp()`) от этого множителя **не зависит** — награда всегда полная, это осознанное решение.
- **Уровни/ранги**: EXP → левел-ап → ранг (E/D/C/B/A/S/National/SSS/Shadow Monarch) через `getRank()`.
- **Титулы**: иерархия значимости `TITLE_PRIORITY` (важнее → менее важно). Новый титул авто-надевается только если он значимее текущего активного; иначе просто добавляется в список. Ручной выбор — клик по карточке в Инвентаре. «Целеустремлённый» требует непрерывной серии 7 дней и полностью пропадает при её прерывании.
- **Преодоление предела**: разблокируется с 3 уровня (кнопка физически скрыта до этого момента), 2 использования в день (плюс бонусы от артефакта/статов/расходников — см. версии v5.8.0+), сбрасывается ежедневно. Расположена выше сетки 2×3 (между последним упражнением и кнопками), визуально отделена разделительной линией.
- **Система штрафов (с v7.5.0 — прогрессивная):** штраф = опыт до следующего уровня × % (`computePenaltyAndApply`). База `penaltyBasePct(level)` = **20%** + 1% за каждые 10 уровней (30% на 100-м; до v7.5.8 — 15%); Сила −0,15% за очко выше 10 (`PENALTY_STR_STEP`), минимум 5% — до нарастания; множитель дня — ступень `penaltyStreakMult(data.penaltyStreak)` (с v7.5.8 `PENALTY_STREAK_STEPS`: ×1 / ×1,5 / ×2 / ×2,5 / ×3 / ×3,5 / ×4 / ×4,5 / ×5, дальше ×5 — потолок на 9-м штрафе подряд; до v7.5.8 — до ×3), **под Бременем — ×3 к ступени** (×3 … ×15; с v7.5.2, было «больший из ступени и ×3» — на длинной цепи Бремя переставало действовать; решение пользователя: «штраф втрое — по-честному», тексты «в 3 раза / утроен / втрое» верны); затем Амулет Воли ×0,85; руны: обычная ÷2, Надёжная/Абсолютная — 0; нехватка — в долг, потолка нет. `data.penaltyStreak` — штрафов подряд: штраф (и под обычной руной, и под Бременем) +1 (внутри `computePenaltyAndApply`, так же у Длани), выполненный день — 0 (`applyPenaltyLogic`), Пелена / Заморозка / полная защита руной — без изменений; несколько пропущенных дней — каждый следующей ступенью. У всех с v7.5.0 — с 0 (без пересчёта по Летописи). Отречение отключает Силу и Амулет. Видно: строка «Штрафов подряд: N» в Статусе (оранжевая, `.sc-debt.sc-pstreak`, только при N ≥ 2, не в шапке) и в окне штрафа (при N ≥ 2); процент в окне — итоговый. Глава «Наказание за Слабость» описывает это без чисел. **С v7.5.10 — тяжесть и «подряд» раздельно (решение пользователя):** `data.penaltyStreak` — **тяжесть штрафа** в шагах (0 = ×1 … 8 = ×5, `PENALTY_SEV_MAX`): штраф +1 шаг (до 8), **выполненный день −2 шага (−1,0, `PENALTY_SEV_DROP`), не ниже ×1** (было — сброс); `data.penaltyRun` — **штрафов подряд**: штраф +1, выполненный день — 0. Пелена, Заморозка, полная защита руной, руны отмены штрафа — обоих не меняют. Поле `penaltyRun` — в шаблоне, переносе (нет поля — из `penaltyStreak`: до 7.5.10 они совпадали), проверке при загрузке, `sanitizeImportedData`; тяжесть при загрузке и импорте — не выше 8. Показ: Статус — «Тяжесть штрафа: ×N» (при > ×1) и «Штрафов подряд: N» (при ≥ 2), оранжевые (`.sc-pstreak`), не в шапке; окно штрафа — «Тяжесть штрафа: ×N» (множитель этого штрафа, без Бремени, при > ×1) и «Штрафов подряд: N» (≥ 2); Длань — счётчики «Тяжесть штрафа» (×1…×5, шаг 0,5) и «Штрафов подряд» (0…10), «Сбросить цепь штрафов» — оба к нулю; строка «Ступень следующего штрафа» убрана. Выход с ×5 до ×1 — 4 выполненных дня; режим «3 провала / 1 выполненный» постепенно доводит до ×5. Кодекс: «Каждый следующий провал обходится дороже предыдущего, а выполненное задание лишь постепенно снижает тяжесть штрафа.» **v7.5.8 (решение пользователя):** штрафы были слабые — база 15 → 20%, потолок ×3 → ×5 шагом 0,5; Сила, Амулет Воли, руны, Бремя ×3, рост +1% за 10 уровней — без изменений («всё по-честному, по-жёсткому и чувствительно»). Пример: 30-й уровень, Сила 10 — 1035 / 2070 / 3105 / 4140 / 5175 EXP на ступенях ×1 / ×2 / ×3 / ×4 / ×5; Сила 130 и выше — база 5% (225 … 1125); Бремя на потолке — ×15 (15525). **Руны отмены штрафа цепь не откатывают (решение пользователя после v7.5.5):** Руна Очищения, Руна Очищения Судьбы, Руна Искупления и Руна Исправления возвращают опыт, Летопись, статистику и серию дней (каждая — своё, по описанию), но `data.penaltyStreak` не меняют: следующий штраф идёт со ступенью цепи, как если бы руны не было. Тяжесть снижает только выполненный день (с v7.5.10 — на 1,0, до этого — сброс). Это осознанно: отмена штрафа — восстановление потерь, а не прощение пропуска. Тексты предметов о цепи не говорят и не обещают её снять; новые предметы отмены штрафа делать так же, если пользователь не решит иначе. Если понадобится откат: вариант «−1 к цепи за отменённый штраф» обсуждался и не принят. В Длани (с v7.5.7) — счётчик цепи «Штрафов подряд» (− / +, 0…10; больше 10 — только настоящими штрафами), «Ступень следующего штрафа», «Текущий уровень», «До следующего уровня», «Опыт», «Следующий штраф: P% или N EXP» (+ «(с Бременем Аномалии ×3)», строка руны — «вдвое» / «штрафа не будет» / «не сработает — Бремя Аномалии», «Из них в долг») и «Сбросить цепь штрафов»; меняют только `data.penaltyStreak`. Процент штрафа — одна функция `penaltyFraction()` для настоящего штрафа и показа в Длани (`penaltyPreview()` ничего не меняет; руны — по тем же правилам, что в `computePenaltyAndApply`, включая «спящие» под сделкой). «Обнулить общее число штрафов» (бывшее «Обнулить счётчик штрафов») — `totalPenalties`, к цепи не относится. Строка цепи в Статусе обновляется при открытии Статуса (`fillStatusBlock`).
- **Характеристики**: пять статов — Сила (STR), Ловкость (AGI), Выносливость (STA), Интеллект (INT), Восприятие (PER), в этом порядке на экране. Очки начисляются при левел-апе (база + бонусы от артефактов роста статов), распределяются вручную. Подробности эффектов каждого стата и цифры — см. записи v5.9.9–v5.9.10.
- **Системные уведомления**: 3 типа (утро/срочно/выполнено), у каждого 2–3 обезличенных варианта текста (Система обращается как «Игрок», никогда не по имени — так по лору первоисточника). Показываются не чаще раза в день, флаги в `data.dailyNotices`.
- **Имя игрока**: спрашивается один раз при первой установке (не при миграции старых сохранений), хранится в `data.playerName`, можно сменить из «АРХИВА». Фолбэк-подпись — «Игрок» (не «Охотник» — сознательно отвергнутый вариант).
- **Журнал/календарь («Летопись»)**: отдельная кнопка (не вкладка — так было в v5.6.0, переделано в v5.7.0). `data.history` — запись на каждый день (статус success/penalty/protected + опционально достигнутый уровень), ключ — календарная дата **начала** цикла заданий (сдвиг через полночь до 5 утра учтён в `checkMissedDays()`, дата берётся от `data.lastReset` до его обновления). `data.bestStreak` — рекорд серии, обновляется в `applyPenaltyLogic()`. `data.pendingLevelUpToday` — служебное поле, перезаписывается на каждый левел-ап в течение дня, «прикрепляется» к записи истории при суточном сбросе и обнуляется. История ведётся с нуля от даты обновления (ретроактивно не восстанавливается — это ожидаемо). Цвета: зелёный/красный/синий — обводка+свечение (не заливка), сегодняшний день — рамка из 4 уголков синим. Пурпурный в календаре не используется — он закреплён только за рангом Shadow Monarch.
- **Кодекс Системы**: отдельная кнопка, список глав (`CODEX_CHAPTERS`) с **индивидуальной нумерацией** — `data.codexUnlocked` хранит порядок открытия лично у этого игрока (не привязан к теме), поэтому дыр в номерах не бывает. Базовые главы (`daily_quota`, `penalty`, `chronicle`, `shop`, `boxes`, `archive`, `stats`) есть у всех с самого начала без уведомления. Остальные главы (ранги через `RANK_CODEX_MAP`, артефакты `artifact_*`, три титула через `TITLE_CODEX_MAP`, `limit_break` — с 3 уровня) открываются функцией `unlockCodexChapter(id)`, которая уведомляет («Записано в Кодекс: …») и является идемпотентной (безопасно вызывать повторно). Чтобы добавить новую главу под будущий предмет/фичу — просто дописать запись в `CODEX_CHAPTERS` и вызвать `unlockCodexChapter()` в нужном месте, механизм это и есть весь его смысл.
- **Прогресс**: отдельная кнопка, показывает то, что раньше было текстом на главном экране («Общий прогресс за всё время»).
- **Нижние кнопки**: сетка 2×3 (`sub-menu-grid`) — Кодекс/Летопись/Архив, Магазин/Инвентарь/Прогресс.
- **Очередь системных уведомлений**: единый механизм (`enqueueNotification`/`processNotificationQueue`/`displayNotificationNow`) для ВСЕХ типов сообщений (короткие баннеры через `showNotice()`, объявления о ранге/титуле через `showSystemPopup()`, Кодекс). Не более одного на экране одновременно, автозакрытие через 10 секунд или тап раньше, пауза 2 секунды между показами. Надписи COMPLETE (`completeFx`) и LEVEL UP (`levelUpFx`) в очередь не входят, но с v7.4.4 очередь ждёт их конца (сцена `fxS`, см. запись v7.4.4; задержки 4,5 с из v5.7.13 — только когда надписей нет).
- **Журнал уведомлений за сутки**: `data.notificationLog` (время + текст, самые новые сверху), пишется в `logNotification()` при каждом показе, сбрасывается при суточном сбросе. Доступ — кнопка «Уведомления системы» в «АРХИВЕ» (секция «Игрок»).
- **Напоминания о невыполненном задании**: категория переименована из «Срочно» в «reminder» (в коде: `SYSTEM_NOTICES.reminder`/`reminderUrgent`). Проверяется каждый час в окне 10 часов до сброса (`checkReminderNotice()`, `data.remindersFiredHours` — какие часовые отметки уже показаны сегодня), последние 2 часа — более настойчивый пул текстов. Прекращается сразу при выполнении задания.
- **Защита от повтора текста**: `pickRandomNoRepeat(pool, category)` — не показывает тот же текст, что был в прошлый раз в той же категории (`data.lastNoticeText`). Используется для morning/complete/reminder.

**`APP_VERSION`** — JS-константа (в начале скрипта, рядом с `STORAGE_KEY`) с номером текущей версии в виде строки (например, `'5.7.9'`). Обновлять её при каждом бампе версии — вместе с `<title>`, `CACHE_VERSION` в `sw.js` и этим файлом. Отображается тихой строкой в модалке «АРХИВ» (раздел «Версия», над «Игрок») — это позволяет пользователю быстро сверить на телефоне, что открылась именно новая версия, а не старая закэшированная.

**Уведомления о прогрессе дня (20/40/60/80%)** — `countDoneQuests()` считает, сколько из 5 заданий закрыто. Каждый раз, когда одно из пяти упражнений достигает своей цели (в обработчике клика `+`), проверяется `countDoneQuests()*20`; если такой процент ещё не показывался сегодня (`data.progressNoticesShown`) и это не 100% (100% уже покрыто существующей категорией «Выполнено»/`dailyNotices.complete`) — показывается `showNotice('Задание дня выполнено на X%.', 'info')`. Один шаблон текста на все пороги, без вариаций. Массив `progressNoticesShown` сбрасывается ежедневно вместе с остальными daily-полями; не сбрасывается при активации «Преодоления лимита» (специально, чтобы повторное прохождение дня не спамило те же уведомления заново).

**Стилистика Кодекса (важное правило для будущих глав):** текст в `CODEX_CHAPTERS` — финальный, согласован с пользователем построчно (v5.7.1). Любые новые главы должны выдерживаться в той же стилистике:

- Ранги не «присваиваются Системой» (по лору статус/ранг выдаёт внешняя Ассоциация Охотников, а не личная Система игрока) — вместо этого Система **констатирует факт** пересечённого порога («Первый этап эволюции...», «Достигнут устойчивый прогресс...»).
- Артефакты не «вручаются» — используется нейтральная формулировка «Получен артефакт: …».
- Избегать сюжетных отсылок к событиям/механикам, которых в приложении физически нет (например, для Shadow Monarch — никаких «теней восстают», это не бой с монстрами; акцент на реальный факт — эволюция через тренировки, абсолютный предел системы измерения).
- Термин «штраф» (не «взыскание») — уже устоявшийся в интерфейсе (заголовок баннера, Летопись), использовать именно его.
- Термин «задание» (не «норма»/«норматив») — уже устоявшийся, использовать именно его.
- Конкретные числа в тексте (проценты бонусов и т.п.) должны точно совпадать с реальными значениями в коде (например, Кольцо Спешки — 10%, Амулет Воли — 15%) — Кодекс это справочник, который не должен врать о механике.

**Уроки (не повторять):**
- Не переделывать модальные окна (`.status-window`) на схему «закреплённый заголовок / скролл только тела / закреплённая кнопка» через `overflow:hidden` на окне + `dvh`/JS-подстраховку высоты — пробовали в v5.7.3–v5.7.5, ломало мобильный Chrome (контент вылезал за окно, кнопка «Закрыть» переставала работать). Текущая рабочая архитектура (с v5.7.8) — закреплённый заголовок, скроллится только `.status-body`, кнопка «Закрыть» и HUD-уголки вне зоны прокрутки, **без** `overflow:hidden`/`dvh`/JS-подстраховки.
- При диагностике по скриншоту — всегда уточнять, какой именно файл на скриншоте (реальное приложение или отдельный демо-макет для показа эффекта) — путаница с этим один раз стоила целой сессии ложной отладки несуществующего бага.

## UI/UX-конвенции, которые важно соблюдать

- **Никаких нативных `alert()`/`confirm()`/`prompt()`** — всё оформлено как стилизованные модалки/баннеры в духе «системных окон» (см. `.status-overlay`, `.system-popup`, `showConfirm()`, `showNotice()`). Если добавляешь новое действие, требующее подтверждения или показывающее результат — используй существующие хелперы, не откатывайся на браузерные диалоги.

## Рабочий процесс с пользователем (важно!)

Пользователь **не программист**. Установленное явно правило по ходу разработки: **не писать код без прямой команды пользователя** — сначала обсуждение, план, уточняющие вопросы (что не мешает, а что можно менять — например, дизайн/анимации трогать нельзя без явного разрешения), и только после явного «пиши код» — правки. Это правило нарушалось один раз и было явно зафиксировано пользователем как недопустимое — при работе через Claude Code стоит придерживаться той же логики: сначала план и confirmation, потом implementation, особенно для нетривиальных изменений (баланс, новые механики, структурные правки). Мелкие explicit-командные правки («сделай имя жирным», «сократи до SLDT») можно делать сразу.

При любых изменениях **всегда объяснять пользователю простыми словами**, что и почему меняется — он не разбирается в коде и оценивает результат только по итоговому поведению приложения.

**Номер версии согласуется с пользователем в плане (правило пользователя после отмены v7.6.0):** не повышать среднюю цифру самовольно — после 7.5.9 идут 7.5.10, 7.5.11 и т. д., пока пользователь не скажет иначе; в каждом плане явно писать «Версия: X.Y.Z». Отменённая версия (7.6.0) в репозиторий не попала, следующая работа шла от 7.5.9.

**Порядок работы:** обсуждение → подробный план (что меняется и что нет, тексты дословно) → «пиши код» → код → проверка → запись версии в `CHANGELOG.md`, новые правила — в раздел правил `CLAUDE.md` → архив. **В `CLAUDE.md` записей версий не писать.** Механику, числа, тексты и вид решает пользователь; ничего сверх согласованного не добавлять.

**Выдача результата (архив):** полный архив `solo-leveling-pwa-vX_Y_Z.zip` — `CHANGELOG.md`, `CLAUDE.md`, `LICENSE`, `README.md`, `fonts/`, `icons/` (с вложенными `items/` и `items-s/`), `index.html`, `manifest.json`, `sw.js`, `tests/`. Не класть: `tests/node_modules`, `screenshots/`, `demo/`, временные файлы. Перед выдачей проверить: версия в 4 местах (`APP_VERSION`, `<title>`, `CACHE_VERSION` в `sw.js`, строка «Текущая версия» в README), запись версии в `CHANGELOG.md`, лишних папок нет, число файлов = прежнее + новые. Архив — файлом; демо — один самодостаточный HTML; код кусками в чат не присылать. Отчёт коротко: что изменилось для Игрока, что проверено, что проверить на телефоне.

**Правки только документации (правило пользователя после v7.4.7):** если правка нужна только для документации (`CLAUDE.md`, `CHANGELOG.md`, README), а не для кода, — версию и архив не перевыпускать; запись запомнить и включить в документацию следующей итерации.

**Как работать (советы пользователя, 19.10.2026, сжато):** искать причину, а не обход; если есть риск — сначала убрать сам риск. Предлагать несколько надёжных вариантов с ценой и рекомендацией и смотреть шире: лучшее решение бывает неочевидным, а бывает самым простым.
